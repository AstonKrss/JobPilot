# 岗哨 · JobPilot

**本地优先的求职副驾** —— 把「看到岗位 → 判断值不值得投 → 定制简历 → 跟进沟通」串成一条流水线，简历原文和 HR 聊天记录全部留在本机。

> 不打分焦虑，只回答四个具体问题：这个岗位能不能评、能不能投、差什么、下一步做什么。

名字取「站岗放哨」：你翻到的每个岗位它替你判断，HR 有回音它替你报警。仓库名沿用 JobPilot（Pilot = 领航员），产品名是「岗哨」。

---

## 为什么做这个

招聘平台推荐的岗位，是按**它的**商业目标算的：投递量越高，它对招聘方的价值越大。所以它不会告诉你「这个岗位你不合适，别投了」，也不会告诉你「你差的只是简历上没写的那一行字」。

求职者真正卡住的地方是三个：

1. **判断成本高** —— 一个 JD 看三分钟，一天看二十个，看完还是不知道值不值得投
2. **简历改不动** —— 想针对不同岗位微调，但重排版式比重写还费劲
3. **投完就失忆** —— 投了五十家，谁回了、聊到哪一步，全靠脑子记

JobPilot 只解决这三件事，不做别的。

## 核心设计

### 一、匹配不打分，拆成四个问题

早期版本给每个岗位算一个 0–100 分。实测发现这套机制有**系统性偏差**：

```
[编程开发工程师] 80 分 ← 全库最高
   岗位未限制学历 / 未标注城市 / 未标注性质
   必备技能 60/60 —— JD 只列了 1 项要求，命中 1 项，满分
   经验年限 20/20 —— 岗位未提年限要求，满分
```

**信息缺失被当成了奖励**：字段越少、JD 写得越敷衍的岗位，分数反而越高；写得认真的岗位因为「要求多、命中不满」被扣分。

现在改成四层，每层只回答一个问题：

| 层 | 回答 | 做法 |
|---|---|---|
| **L0 数据闸门** | 这个岗位能不能评 | 标题不是「公司介绍/招聘简章」+ JD 正文 ≥ 100 字 + 至少抽到 2 个关键字段 |
| **L1 硬约束** | 这个人能不能投 | 城市 / 学历 / 届别 / 实习 vs 社招 / 是否外包，二元判断，不参与打分 |
| **L2 能力缺口** | 差什么 | 必备技能命中 x/y，列出未命中的具体项。**清单是事实，分数是猜测** |
| **L3 参考分** | 值不值得排前面 | 仅当信息完整度 ≥ 60% 时显示，且标注「参考分」 |

配套两个修正：
- 缺失字段不再「不扣分」，而是从分母里去掉并降低**信息完整度**（6 个字段：标题/城市/学历/性质/必备技能/经验年限）
- 技能分母过小时按绝对命中数封顶（只列 1 项要求最多算 70%，避免 1/1 满分）

排序键也随之改为：`决策 → 信息完整度 → 缺口数 → 参考分`。先保证结论可信，再谈谁更好。

### 二、三层记忆，装配优先保证前缀稳定

三层存储，职责不同：

| 层 | 内容 | 何时读 |
|---|---|---|
| **L1 画像** | 结构化槽位（城市/岗位类型/薪资底线/硬约束），带证据链与版本历史 | 每次对话都加载（约 300 token） |
| **L2 情节** | 一次会话压成「主题 + 200 字摘要 + 3 条要点」，带向量 | 会话开场召回一次 top-3 |
| **L3 原始对话** | 全量留档，永不删 | 不进上下文，只供追溯 |

**为什么召回只在开场做一次**：模型服务商的 KV Cache 是按前缀匹配的，每轮重新装配 prompt 会让前缀变化、缓存全部失效。一次会话通常只有一个主题，开场召回一次完全够用。

**装配顺序也按这个原则排**：

```
[固定] 系统提示 + 工具定义
[固定] 画像快照（会话开始时取一次）
[固定] 召回背景（开场算一次，会话中不变）
[追加] 对话历史（append-only，不重排不改写）
[末尾] 本轮动态信息（当前时间 / 选中简历）
```

原则是**易变内容一律后置** —— 放开头会让后面全部缓存失效。

**画像更新用三层漏斗，不是每句话都问模型**：

```
L0 规则预筛（零成本）：信号词（只/仅/必须/以后/也可以）× 槽位词同现
L1 异步抽取：输出结构化 {slot, op, value, modality, evidence}
L2 代码裁决：按 modality 决定覆盖 / 合并 / 挂起
```

关键在于**用 `modality`（表述强度）而不是 `confidence`（模型自评信心）**：

| 用户说法 | modality | 动作 |
|---|---|---|
| 「以后只找广州」 | `exclusive` | 直接覆盖，旧值进历史 |
| 「深圳也可以」 | `additive` | 合并进数组，旧值保留 |
| 「杭州可能也行吧」 | `tentative` | 挂起，下轮自然问一句 |

模型给的 0.87 这类信心分基本是编的，同一个模型两次能差 0.3；而「排他 vs 补充」是明确的语义类型，代码一行就能分。

### 三、四层缓存，每层解决不同的浪费

| 层 | 缓存什么 | 失效条件 | 实测收益 |
|---|---|---|---|
| 改写建议 | 某简历 × 某岗位的建议批次 | 简历重新解析 | 省一次 40 秒生成 |
| 匹配结果 | 筛选条件 + 简历画像内容 + 岗位库版本 | 任一变化 | 22.9s → 4ms |
| 向量 | 文本哈希 + 模型标识 | 换模型 | 重启不再重算 |
| 语义判定 | 技能要求 × 简历证据 | 文本变化 | **18.4s → 0.6s** |

**语义判定缓存是收益最大的一项**。每次匹配要把最多 40 对（岗位技能 × 简历证据）交给模型逐对判断，一次 18 秒。但判定只取决于这两段文本，**与是哪个岗位无关**，所以能跨岗位复用——第二次匹配同一批岗位，一次模型调用都不用花。

顺带一个反直觉的实测结论：

```
bge 余弦相似度：正例 0.504  vs  负例 0.513   ← 负例反而更高
```

**向量相似度的绝对值没有区分度，不能拿阈值直接判定**，只能用来召回候选、由模型裁决。任何「相似度 > 0.85 就算命中」的方案都会误杀误放。

### 四、简历改写只改文字，不重排版式

用户上传的简历是自己排的版。他要的是「把项目描述改一下」，不是「换一套模板」。

所以路径是：**DOCX 直接改 run → PDF 先按坐标还原成 DOCX 再改 → 转不动才回退重建**（并在界面明确标注「版式不是原版」）。

PDF 转 Word 有四个通病，都用渲染截图逐页比对修掉了：

| 现象 | 原因 | 修法 |
|---|---|---|
| 时间列被裁掉半个字 | 列宽之和已占满页面还带缩进 | 表格可用宽 = 页面宽 − 缩进 − 0.8cm |
| 换行后文字叠成黑块 | 行高写成 `exact` | 改 `AT_LEAST` |
| 项目名折成三行 | 列宽等比缩放 | 单行表格按显示宽度重分配 |
| 邮箱断成两行 | 6 列等宽 | 邮箱列拉到 3.4cm |

**没有选「直接在 PDF 上替换文字」**：PDF 是固定排版，改字数必然破坏后面的行。「主导」→「负责」这种等长替换技术上可行但语义不够，真要改成「负责后端部分模块开发」就得多 6 个字，整行重排。所以 PDF 必须先有可编辑结构。

改写还有两条硬约束：
- **不能丢内容**：给模型的输入是段落全文（不是截断版），改写后短于原文 60% 直接拒绝
- **职责降级必须放行**：「我主导后端架构」→「我负责后端部分模块开发」相似度 86%，会被空话拦截误杀。判据是「原文有抬高词、改后没有了」——这是收敛表述，不是注水

### 五、多平台适配：不猜类名，认结构

跨 BOSS / 猎聘 / 智联三个平台，踩过的坑比功能本身多：

| 问题 | 后果 |
|---|---|
| 用了尚未声明的常量（TDZ） | 顶层抛错，**所有平台**都不出 UI |
| 路径正则只认 `/job_detail/`，智联是 `/jobdetail/` | 详情页被判成列表页 |
| 卡片链接写死 `a[href*="job_detail"]` | 智联链接全取不到，抓取结果为空 |
| 类名猜成短横线 `.job-card-pc-container`，实际是驼峰 `.jobCardPcContainer` | 42 张卡片一张都没命中 |

写通的教训：

1. **驼峰和短横线都要试**，平台各版本不一致
2. **聊天页不认类名，认结构** —— 智联 IM 的 `message-item` / `chat-item` / `chat-msg` 全是 0 节点（类名是构建产物）。改成以输入框为锚点向上找聊天区、区内取 DOM 最深的可滚动容器、用元素中心横坐标判说话人
3. **独立子域比路径可靠** —— 猎聘沟通页是 `c.liepin.com`，路径就是一个 `/`，连 `chat` 字样都没有
4. **诊断要输出类名频次** —— 选择器全不命中时，光说「不命中」没法改；把页面上与岗位/消息相关的类名按出现次数列出来，一次就能写对

### 六、人机边界：发送永远由人点

扩展能填输入框，但**不点发送**。三个理由：

1. **封号**：平台有行为检测（发送频率、时间规律、鼠标轨迹），批量自动发是最典型的封禁特征
2. **责任**：自动发出的话代表你本人，「薪资可以谈」「下周到岗」说错了收不回
3. **条款**：多数平台明确禁止自动化操作，踩线的是用户账号

对照的是「只读」的自动化——自动检测 HR 回复、自动同步聊天记录，这些没有风险，就做了。

同理，「补技能」这个功能也守一条线：用户说「我会 Linux」时，**只在技能段落里追加一个词**，绝不去改项目描述。如果简历里没有独立的技能段落（实测很多学生简历没有），就**明确拒绝改文件**，只更新内部画像并告诉用户「建议你自己加一行技能」。找不到合适位置就不改，不做近似猜测。

### 七、岗位雷达：先判能不能进，再判值不值得去

匹配页回答「这个岗位和我有多匹配」，但它不回答一个更前置的问题：**这个岗位我根本进不去吗。**

雷达把顺序改成：方向 → 可达性 → 公司质量 → 匹配度 → 距离。

**第一道是方向。** 第一版没有这道，结果「秩序类管培生（物业安全管理方向）」排到了第一：公司是美的系（分高）、城市佛山（近）、学历不限、经验不限 —— 每一项硬约束都合格，唯一的问题是它跟 Java 后端没有任何关系。硬约束全是"没违反"，于是全部放行。教训是：**方向不对口不是"分数低一点"，是"不在射程内"**，必须单独成一道闸门，不能压缩进分数。

**第二道是可达性。** 届别、学历、经验、通勤、岗位性质，逐项二元判断：

| 你的情况 | 判为不可达的典型 JD |
|---|---|
| 2028 届 | 「27 届管培生」（标题正则兜底，老数据没抽届别字段也能判） |
| 本科 | 「要求硕士」 |
| 0.7 年实习 | 「3 年以上」—— 佛山大量 Java 岗是社招岗，校招投过去没有回音 |
| 佛山/广州 | 深圳、杭州、北京 |

**第三道才是公司质量。** 这是「优质」被真正量化的地方。判「美云智数适不适合我」的四个理由 —— 在佛山、不是互联网大厂、不卡学历、是美的子公司 —— 全是公司级事实。而原来的岗位画像一条都没有，只能对每个岗位单独猜。

公司画像单独一张表，一条记录服务该公司所有岗位：

```
base 55
  母公司背书      +10    美的集团旗下
  行业方向        +14    工业软件 / 制造业数字化
  上市/国企       +9
  有校招通道      +5
  互联网大厂      −12    简历筛得最狠
  外包/人力       −32    签的是服务商，简历贬值
  历史 JD 硕士比例 阈值 30%，样本 < 3 条时忽略
```

结果是「美云智数 86 分 / T0 首选」，与用户自己凭直觉给出的判断一致 —— 这说明规则抓住了他真正在意的东西，而不是拟合了一个分数。

**为什么必须说"没有"**：45 个岗位的库里，雷达只推出 6 个可投，且没有一个来自优先梯队。这个结果不好看，但它是真的。界面上直接写出来，并指向下一步（该搜什么词、该按哪家公司直搜），而不是用排序好看的卡片盖住它。

**届别字段是新加的**：JD 写「2028 届」「27 届」时抽 `graduate_years`，配合 `campus_type`（校招/实习/社招）。校招场景下这是用户最先看的一个信号，而原来的抽取完全没碰它 —— 「27 届管培生」和「28 届校招」在列表里长得一模一样。

### 八、主动发现与消息监控：代价是必须开标签页

求职期真正要盯的是「有没有人回我」和「还有哪些岗位没看到」。这两件事都得平台登录态下才有数据，所以只能靠浏览器真的把页面打开一次。

**HR 消息监控**

后台每 10 分钟开一个标签页打开聊天页（不抢焦点，跑完关掉）→ 找未读会话 → 逐个点开读消息 → 上报 → 有 HR 新消息才弹通知。

三个必须说清的点：

1. **只有 HR 说的才算新消息。** 同步接口按角色分开计数（`added_hr` / `added_me`）。混在一起的话，用户自己刚打完一句话也会弹「HR 有新消息」——通知误报两次之后就再没人点它了。
2. **点开会话会清掉平台上的未读红点。** 这既是副作用也是目的：消息已经进本地库，红点留着只会重复提醒。
3. **未读识别靠徽章尺寸。** 平台会把所有会话渲染出来再隐藏，隐藏的那些也有 class 名。只按 class 匹配的话每次检查都报「有 5 个未读」，所以判定条件里加了「元素必须有实际尺寸」。

**一键发现**

搜索计划算出关键词后，在同一标签页里换词、翻页、入库：

```
打开起点 URL → 在搜索框输入关键词 → 等结果变化 → 翻 N 页 → 下一个关键词
```

不在后端拼搜索结果 URL，理由是**失败形态不同**：URL 拼错的表现是「打开了一个正常页面，但结果和你搜的词无关」，看起来像抓取坏了；而在搜索框里打字是真人做的事，参数由平台自己处理，坏的时候表现是「搜索框没找到」——一个能直接说出口的原因。

换词这一步有个坑：**直接改 `input.value` 不会触发 React 的 onChange**，状态不更新，按回车搜的还是旧词，控制台干干净净。必须用原型上的 setter 赋值，再补发 `input` / `change` / `keydown` 三个事件。

**随浏览自动收录**

比"点按钮"更进一步：用户翻到哪，插件就把哪收进来。三条路径同时生效：

| 你在做什么 | 插件做什么 |
|---|---|
| 打开岗位详情页 | 稳定 2 拍后自动入库完整 JD，然后**当场给出判定**：「可以投 · 美的集团旗下 · T0 81 分 · 同城」或「别投：要求 3 年以上，是社招岗」 |
| 翻列表页 | 自动把当前页前 12 条摘要收进来（每个 URL 只扫一次），面板显示「已收录 N 个新岗位」 |
| 打开 HR 聊天页 | 立即同步一次，之后消息区一有变化就同步（1.2 秒防抖），不再等 60 秒轮询 |

判定必须发生在抓取现场：等用户想起来去「发现」页翻，这个岗位多半已经关掉了。单个岗位的判定走 `GET /api/radar/job/{id}`，和雷达列表共用同一个 `_build_item()`——两处口径分开写，同一条岗位会显示两种结论。

列表页只抓当前页、不自动翻页：翻页会打断用户正在看的列表，也更容易被风控盯上。卡片是异步渲染的，所以抓不到时会重试最多 20 拍（约 18 秒）再放弃，而不是"进页面那一秒没卡片就永久跳过这一页"。

## 架构

```
┌──────────────┐   ┌──────────────────────────────────────────┐
│ 浏览器扩展    │   │  FastAPI 本地服务                          │
│ (MV3)        │──▶│                                          │
│              │   │  抽取：PDF/Word → 结构化画像                │
│ 岗位页：      │   │  匹配：硬约束 → 缺口 → 参考分               │
│  抓 JD       │   │  改写：保版式 docx 编辑                     │
│ 聊天页：      │   │  记忆：画像 / 情节 / 原始对话                │
│  读消息      │   │  投递跟踪：状态机 + 时间线                   │
│  提回复      │   │                                          │
└──────────────┘   └────────────┬─────────────────────────────┘
                                │
                   ┌────────────▼─────────────┐
                   │ PostgreSQL（本机 :5433）   │
                   │ 岗位 / 简历 / 匹配缓存      │
                   │ 投递跟踪 / 聊天 / 记忆      │
                   └──────────────────────────┘
```

数据全部落在本机。只有「抽取 / 改写 / 语义判定 / 摘要」这几步会把**必要文本**发给模型服务，不发文件本身。

## 快速开始

### Windows：双击 `start.bat`

首次运行会自动创建虚拟环境并装依赖（3–5 分钟），之后每次启动都只要几秒。

前置条件只有两样：

| 依赖 | 说明 |
|---|---|
| Python 3.11+ | 安装时**务必勾选** "Add Python to PATH"。虚拟环境由 `start.bat` 自己创建 |
| PostgreSQL 14+ | 只用来存数据。装好后把 `bin` 目录写进 `.env` 的 `POSTGRES_BIN`（见下） |

`start.bat` 会依次做这些事，任何一步失败都会停下来并说明原因，不会一闪而过：

1. 没有 `.env` 就从 `.env.example` 复制一份，并提示填 `LLM_API_KEY`
2. 没有 `.venv` 就创建虚拟环境并装依赖
3. 找 `postgres.exe`（依次查 `POSTGRES_BIN` → PATH → conda 环境 → 官方安装目录）
4. 起数据库，**等到端口真的能连上**才继续
5. 起后端（日志直接打在这个窗口里）
6. 轮询 `/health`，等后端真的响应了才打开浏览器 —— 先开浏览器再起服务是最常见的"怎么打不开"来源

停止：`Ctrl+C` 或关窗口。数据库会一起关（走 `pg_ctl -m fast`，不是杀进程，避免下次启动走崩溃恢复）。如果直接点了窗口右上角的 ×，数据库可能残留 —— 用 `stop.bat` 收尾，下次启动也会自动复用它。

> `.env` 里的 `POSTGRES_BIN` 支持填目录或可执行文件，例如：
> `POSTGRES_BIN=C:/Program Files/PostgreSQL/16/bin`。不填时脚本会自己找。

### 手动启动（macOS / Linux，或想看每一步）

```bash
pip install -r requirements.txt

createdb ragjob && psql ragjob -f backend/app/db/schema.sql
cp .env.example .env      # 填 LLM_API_KEY；.env 已被 .gitignore 排除

python scripts/fetch_embed_model.py          # 本地 bge-small-zh（90MB，可选）

python scripts/launch.py                     # 等同于 start.bat 的第二步起
```

`scripts/launch.py` 是跨平台的，macOS/Linux 上同样能用（数据库路径通过 `POSTGRES_BIN` 指定）。

### 浏览器扩展是可选的

**不装扩展能完成全部功能**：在招聘网站打开岗位详情页，`Ctrl+A` 全选 → `Ctrl+C` 复制 → 粘贴到「岗位」页的输入框，入库、匹配、改写、工作台全都照常。

装上扩展只是省事：

| | 不装扩展 | 装了扩展 |
|---|---|---|
| 岗位录入 | 复制粘贴 | 点一下自动抓取 |
| HR 聊天记录 | 手动复制到对话页 | 自动同步到工作台，能发现新回复 |
| 安装成本 | 0 | 扩展管理 → 开发者模式 → 加载 `extension/` 目录 |

扩展**只读页面**：不碰输入框、不点发送。回复生成后由你自己按回车 —— 这是刻意的边界，见「人机边界」一节。

## 已知限制

写在这里，因为它们都是**真问题**，不是待办清单：

1. **打分没有校准基准** —— 「80 分」意味着什么，没有外部验证。要让它变准，唯一的路是把投递结果（有没有回复、有没有约面）回灌到打分里。这需要真实使用的数据量，不是改代码能解决的。
2. **多平台适配天然脆弱** —— 平台改版就要修选择器。今天修好猎聘，明天可能又坏。这是所有爬虫类工具的宿命。
3. **服务商生成速度限制** —— 实测约 6 tok/s，比正常 API 慢一个数量级。所有同步链路的体验都受它制约，只能靠异步和缓存绕开。
4. **单人单机** —— 没有并发设计，没有多用户隔离，没有鉴权。它是本地工具，不是服务。
5. **移动端不可用** —— 需要电脑、Python 环境、浏览器扩展。这筛掉了真正在碎片时间刷岗位的那部分用户。
6. **公司画像的预置数据会过时** —— 58 家公司的母公司、行业、所在地来自公开资料，写死在 `radar/seed_companies.py` 里。收购、搬迁、上市状态变化都不会自动跟上，所以界面上每条都能改，改过的字段会锁定、不再被自动学习覆盖。学历门槛刻意不预置，只从该公司历史 JD 的硕士要求比例统计 —— 编一条假的学历门槛比留空更糟。
7. **通勤只有城市级精度** —— 不接地图 API，所以只能区分「佛山同城 / 广佛邻市 / 超范围」三档。同在佛山，顺德北滘和南海桂城被算成同一档，实际通勤差一小时。要做准必须引入地理编码与路径规划，那会多一个外部依赖和一份 API key。
8. **自动化的前提是浏览器开着** —— 消息监控与一键发现都要开真实标签页（平台数据在登录态 + 客户端渲染之后，没有可直接调用的接口）。浏览器关掉、或登录态失效，它们就只是安静地「抓到 0 条」，不会报错。界面上把最后检查时间写在弹窗里，就是为了让「没动静」和「坏了」能区分开。
9. **未读识别与搜索框都是猜的** —— 各家平台类名不同、还会改。未读靠徽章尺寸 + class 关键字，搜索框靠 placeholder/id 候选列表。猜不中时的表现是「有未读但读不到内容」和「找不到搜索框」，两种情况都会在弹窗里给出具体原因，而不是静默失败。
