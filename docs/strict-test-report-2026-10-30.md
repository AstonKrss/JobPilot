## 三、新发现的缺陷

### 3.1 【中】并发同 JD 入库去重失效（竞态窗口）

```
6 线程同时 POST /api/jobs/ingest（同 URL + 同正文）
→ 返回 6 个不同的 job_id：[101, 100, 98, 96, 97, 99]
```

- **对照**：同文件并发上传 ×8 只创建 1 条（`reused=[False, True ×7]`）；投递并发创建被数据库唯一约束兜住。**唯独岗位入库的去重是应用层 check-then-insert，两步之间无锁、无唯一索引**。
- **影响**：扩展的批量采集是并发跑的——同一个岗位被两条列表项触发就会重复入库。串行去重（上一轮已验证）掩盖了这个窗口。
- **建议**：`job` 表加部分唯一索引 `(source, coalesce(url,'')) WHERE url IS NOT NULL`，`create_job` 改 `INSERT ... ON CONFLICT DO NOTHING ... RETURNING`，冲突时查回既有 id 并置 `reused: true`——与简历上传的语义对齐。

### 3.2 【低-中】docx 解析失败把内部异常类名暴露给用户

```
E3 伪装 docx  → parse_error = "内部错误：PackageNotFoundError"
E4 宏文档     → parse_error = "内部错误：KeyError"
E5 zip 炸弹   → parse_error = "内部错误：KeyError"
E8 空 docx    → parse_error = "内部错误：KeyError"
```

解析任务的兜底 `except` 直接把 `str(exc)` 写进 `parse_error`。三个问题：用户看不懂；「内部错误」四个字配上类名反而像系统坏了；类名属于内部实现，不该进用户可见的 UI。**对照**：PDF 链路的错误处理是范本——「有密码保护，无法读取内容。请导出无密码版本后重试」。建议 docx 链路按异常类型映射成同样的用户语言。

### 3.3 【低】file_name 原样入库，未清洗

`../../evil.pdf`、300 字符文件名都被原样存进 `resume.file_name`。**当前无实际危害**：落盘文件名是 SHA256（实测 `f125c3f4….pdf`），路径穿越不成立；下载/删除正常；前端有 `esc()`。但这是「恰好安全」：一旦导出/下载功能用 `file_name` 拼 `Content-Disposition` 或路径就会踩坑。建议入库时清洗（去路径分隔符、限长）。

### 3.4 【低】`docx_text.py` 无 zip 防护

`Document(path)` 直接读，40MB 解压体积的 docx 全量进内存。本轮靠兜底 `except` 挡住（服务存活），是运气不是设计。python-docx 官方不提供大小防护，建议上传时检查解压后体积（读 zip 目录即可，不解压），超限直接拒绝。

## 四、经受住严格测试的部分

- **X-Y Cut 全量回归**（见第二节）—— 本轮最大的风险点，零回归
- **极端输入 9/9**：加密 PDF 文案明确；损坏 PDF 自动降级 OCR 分支并给出人话提示；伪装 docx / 宏文档 / 空 docx 全部安全失败；**40MB zip 炸弹服务存活**；500 页 PDF 完整解析（`pages=500, done`）
- **并发下的正确性**（除 3.1 外）：同文件并发上传 ×8 只建 1 条；上传后立刻删除，后台解析不复活记录（3 轮全过）；6 线程画像写入不同槽位无丢失；投递并发创建被唯一约束兜住、stats 全程一致
- **安全基线**：1MB JD 11.5 秒正常入库；SSE 发起后立即关闭不阻塞服务；2000 层嵌套 JSON 返回 400；同会话并发 chat ×4 消息不串写
- **规则引擎**：63 条 96.8%，否决 precision/recall 双 100%，无退化
- **白盒第二批**：`sanitize.py`（脱敏启发式的两类误差文档明确、返回被替换原文供核对）、`quality.py`（六项检查全部可从原文核对，"画像里出现原文找不到的字段必须当成严重问题"——反编造意识）、`ocr.py`（引擎懒加载锁 + predict 互斥锁、OCR 像素坐标统一换算回 point）——设计质量都很好
