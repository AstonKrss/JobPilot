# Agent 与记忆系统 · 产品级评测报告

- **被测对象**：`http://127.0.0.1:8000/` 的对话 Agent（PlanAgent + ChatAgent）、记忆系统（长期画像 + 情节记忆）、岗位召回与匹配引擎
- **评测时间**：2026-10-29 20:22 – 20:40
- **方法**：标注集 + 真实请求 + 白盒代码审计 + 对照实验
- **数据规模**：80 岗位 / 5 简历 / 2 条既有情节记忆 / 3 个画像槽位
- **总评**：**感知层做得很好，执行层不达标。** 意图识别、槽位抽取、规则判定都达到可用水平；但「按意图召回岗位」和「把记忆真正用起来」这两件核心的事没有实现。

## 三、核心问题（P0）

### P0-1 对话里说的偏好，系统一条都没记住

**这是本次评测最严重的问题：助手会答应，但不会记录。**

实测（20:34，真实请求）：

```
用户：我不接受外包，以后只找佛山的岗位，记住了
助手：记住了：以后只找佛山的岗位，且排除外包。之前的方向是 AI Agent 后端，
      需要我按佛山 + 非外包 + AI Agent 后端帮你检索吗？

数据库复核：
  cities            仍为 ["广州", "深圳"]     ← 没有变成佛山
  user_profile_history  新增 0 条
  episode               新增 0 条
```

**根因（白盒）**：`backend/app/chat/agent.py` 的 `handle_message()` 从头到尾没有调用 `observe()` 或 `summarize_conversation()`。全项目 grep 结果：

```
summarize_conversation 的调用点：只有 backend/app/api/memory.py:25（路由本身）
profile/observe 的调用点：     只有 backend/app/api/profile.py:61（路由本身）
前端 app.js：                   没有调用这两个接口（grep "summarize" 无结果）
```

也就是说，记忆系统有完整的**读**链路（`recall_block` 确实被注入 prompt，实测 slots 里有内容），但**写**链路从未接入对话流程，只能靠手动调 API 触发。

这解释了为什么画像只有 3 个槽位、最后更新停在 10-23，而情节记忆只有 2 条 —— 不是用户没说过，是系统没在记。

**风险**：用户被告知"记住了"，实际什么都没发生。这比不记住更糟：用户的预期被建立起来了。

### P0-3 意图不参与召回，检索实际是「按简历匹配度排序」

`backend/app/chat/agent.py:298-322`：

```python
results = rank(profile, jobs, prefs, semantic)     # 对全部岗位打分，不看意图
sims = _semantic_order(intent, queries, jobs)      # 意图只算相似度
passed.sort(key=lambda r: (group_order[r.decision], -((r.score or 0) + sim * 10)))
```

意图的唯一作用是 `+ sim*10`。而 `score` 是 0-100 的简历匹配分，`sim` 只有 0.58-0.61 —— 实测「产品经理」意图：

| job_id | title | score | semantic_sim | sim×10 | 最终排序依据 |
|---:|---|---:|---:|---:|---|
| 6 | 资深后端工程师 | **80.0** | 0.584 | 5.84 | 85.84 |
| 32 | 前端开发工程师 | 48.0 | **0.607** | 6.07 | 54.07 |
| 34 | 应用软件开发工程师 | 48.0 | 0.592 | 5.92 | 53.92 |

两个致命细节：
1. **sim 的差异只有 0.023**，乘以 10 等于 0.23 分，而 score 的差距是 32 分 —— 意图**在数值上完全无法改变排序**
2. **sim 本身没有区分度**：对「产品经理」而言，前端岗（0.607）比后端岗（0.584）更"相关"，这既反直觉，也说明 `_job_doc()` 拼的"标题+城市+技能"文本信息量太少

结果：**「我想找产品经理的岗位」返回 3 个岗位，0 个是产品岗**，而库里有 5 个（B端产品经理、产品顾问、产品实习生、Tob项目经理、工业AI智能体项目经理）。

同一现象在 8 个意图上重复：`资深后端工程师`（job 6）在 8 个意图里出现了 **7 次** —— 因为它的简历技能匹配分最高，与用户这轮想找什么方向无关。

### 4.2 记忆写入

```
槽位级：TP=8  FP=0  FN=5   precision=100.0%  recall=61.5%  F1=0.762
modality 判定：6/6 = 100%（exclusive / additive / tentative 全对）
负例洁净率：13/13 = 100%（闲聊、提问、临时条件、比较提问全部正确地不记）
```

**precision 满分、负例零误报**，这层做得扎实。问题全在 5 个 FN，而且**全部是 L0 规则预筛拦掉的，不是模型抽错**：

| 用例 | 文本 | 为什么被 L0 挡 |
|---|---|---|
| M05 | 我是 2028 届本科 | 无信号词（"我是"不在 `SIGNAL_WORDS`） |
| M07 | 暂时不考虑字节跳动 | `excluded_companies` 没有任何 `SLOT_HINTS` 词表 |
| M09 | 一定要双休 | `hard_constraints` 没有 hint 词表 |
| M10 | 我优先看大厂 | `target_roles` 没有 hint 词表 |
| E03 | 我想找杭州或宁波的 | 有城市词"杭州"，但无信号词 |

`should_extract()` 要求**信号词 AND 槽位词同时命中**，而 10 个可写槽位里有 4 个（`target_roles` / `hard_constraints` / `excluded_companies` / `accept_relocation`）根本没配 hint 词表 —— 意味着这 4 个槽位**几乎写不进去**。这也解释了为什么库里只有 3 个槽位有值。

### 4.3 记忆召回（三组对照实验）

同一批 12 条标注记忆、12 个改写 query，只改环境变量：

| 组 | 条件 | recall@1 | recall@3 | MRR | P@3 |
|---|---|---:|---:|---:|---:|
| **A 现状** | 既有记忆 hit_count=57/17，时间较新 | **0.0%** | 33.3% | 0.111 | 0.333 |
| **B 隔离** | 既有记忆时间改到 400 天前、hit_count 归零 | 33.3% | 33.3% | 0.333 | **1.000** |
| **C 纯语义** | 12 条测试记忆统一为 1 天前 | **41.7%** | **75.0%** | **0.583** | **1.000** |

三组差异证明了两件事：

1. **A→B：只把旧记忆的时间改老、命中归零，recall@1 就从 0% 变成 33.3%，P@3 从 0.333 变成 1.000。** 说明现状下既有记忆在"霸榜"，把真正相关的记忆全挤出去了。
2. **C 组 recall@3 = 75%**，说明向量检索本身是可用的；但 recall@1 只有 41.7%，排序精度不够。

**根因一：权重设计让"新"和"常被召回"压过"相关"**

```python
score = 0.55 * sim + 0.25 * time_decay + 0.20 * min(hit_count/5, 1.0)
```

时间 + 频次 = **0.45 的上限**，而相关性只有 0.55 的份额。具体败例：

```
query「外包的岗位到底能不能去」
  #7  外包岗位利弊判断        sim=0.764  score=0.600   ← 排第 3
  #2  求职助手模型身份询问     sim=0.494  score=0.722   ← 排第 1
```

**相似度 0.764 输给 0.494，因为后者更新、被召回更多。** 这就是"相关性被时间挤掉"的直接证据。

**根因二：`hit_count` 只增不减，且 5 次就饱和**

```
id 1  评估深圳AI Agent后端岗位匹配   hit_count = 57
id 2  求职助手模型身份询问          hit_count = 17
```

两条都远超饱和点 5，`freq` 项永远是满分 0.20。而 `recall()` 每次命中都 `hit_count + 1`，没有衰减、没有上限外的抑制 —— **被召回过的记忆会更容易被再次召回**，形成正反馈。库里的记忆越多，这个偏差越严重。

**根因三：没有相似度阈值，任何 query 都返回 3 条**

```
q=今天天气怎么样        返回 3 条，最高相似度 0.294
q=帮我写一个快速排序     返回 3 条，最高相似度 0.404
q=推荐几部好看的电影     返回 3 条，最高相似度 0.149
```

即使相似度只有 0.149，也会把 3 条无关记忆注入 prompt。闲聊时 agent 会被塞进一堆"过往结论"。

**根因四：长摘要成为「万能磁铁」**

C 组失败案例里，`正浩 EcoFirst 实习岗评估` 对 7 个不相关 query 的相似度都在 0.39-0.57：

```
q=谈工资       sim=0.394 → 排第 1
q=专科投本科岗  sim=0.568 → 排第 1
q=实习转正     sim=0.545 → 排第 1
```

摘要越长、覆盖词汇越广，向量越接近语料中心，对所有求职话题都有中等相似度。这是摘要式记忆的固有陷阱，需要在入库时限制长度或做多向量拆分。

### 4.4 记忆裁决逻辑（单测 17 项）

`decide()` 的 modality → 处置映射全部正确。但 `_merge()` 有一个**静默数据丢失**风险：

| 场景 | 当前行为 | 风险 |
|---|---|---|
| `additive` + `op=add` | 合并数组 ✅ | 正常 |
| **`additive` + `op=replace`** | **直接覆盖** | 用户说"深圳也可以"，广州被丢掉 |
| **`additive` + 缺 `op`** | **直接覆盖**（默认 replace） | 同上 |

`decide()` 对 `additive` 返回 `apply`，而 `_merge()` 只有 `additive` **且** `op=="add"` 才合并。提示词里没有任何一处强制 `additive` 必须配 `op=add`，完全依赖模型自觉。历史数据里有一条正确合并的记录（`cities: ["广州"] → ["广州","深圳"]`），说明模型多数时候会给 add，但这是**运气，不是约束**。

### 4.5 意图路由与槽位

```
action 分类  15/16 = 93.8%     （唯一错误：I10「佛山有什么岗位」不该直接检索）
intent 命中  16/16 = 100%      （"后端实习"、"AI 相关后端岗"、"Python 后端方向" 都准确）
cities 准确  16/16 = 100%      （"佛山或广州都行" → ["佛山","广州"] 正确）
多轮继承     2/2 组           （"那广州呢" 正确把城市从佛山切到广州，intent 保持"后端方向"）
延迟         P50 5.9s / P90 8.3s / max 11.7s
```

**槽位层是全系统质量最高的部分**，单轮和多轮都稳。

唯一错误 I10「佛山有什么岗位」：模型没给 clarify，`intent` 为空，但代码仍走了检索分支（`elif clarify:` 才澄清），于是用一个空意图检索，返回 6 个岗位。**代码缺少兜底：intent 为空且 slots 无 intent 时应强制澄清，而不是把全部岗位按分数倒出来。**

### 4.6 匹配规则引擎

```
用例 63 条（原 42 + 新增 21）  准确率 61/63 = 96.8%   95% Wilson 区间 89.1%–99.1%
否决判定：TP=21 FP=0 FN=0      precision 100%  recall 100%
按类别：城市 14/14、学历 12/12、工作性质 9/9、技能 14/15、综合 12/13
```

**21 个该否决的全部否决，无一误杀。** 这是整个系统最可靠的部分。

两条"失败"其实是我的标注不如产品严谨：岗位未列任何技能要求时，引擎返回 `confirm` 并给出理由「该岗位未列出任何技能要求，学历/城市/年限通过只代表没被卡住，不能据此判断匹配，建议自行确认」—— **产品判断比我的标注正确**，这两条应记为标注分歧，不计入缺陷。

### 4.7 回复质量

| 约束（来自 `REPLY_SYSTEM_PROMPT`） | 结果 |
|---|---|
| 不贴 URL | 4/4 ✅ |
| 不编造结果里没有的岗位 | 4/4 ✅ |
| ≤250 字 | **1/4** ❌（142 / 306 / 504 / 388 字） |
| 有结论先给结论 | 4/4 ✅ |

回复的自然度和诚实度都很好。典型：

```
问：有没有测试工程师岗位
答：这轮没有找到测试工程师岗位——通过硬约束的 4 个岗位全是后端/前端开发方向，
    没有测试类……若坚持测试方向，建议换关键词重新搜。
```

**它如实说了"没有"，但同时又返回了 4 个不相关岗位。** 问题不在措辞，在召回（见 P0-3）。

题外：问「帮我写个快排」时它写了 504 字带代码块的完整回答。不算错，但与"求职副驾"的定位有偏离，且没有拉回主题。

|---|---|---|---|
| W1 | `agent.py:203` | `recall_block` 只在会话开场召回一次并写死进 slots | 长会话中用户改主意，旧记忆仍在 prompt 里；新记忆不会进来 |
| W2 | `chat.py` 返回结构 | 不返回 plan 的 `clarify` / `chat` 判定 | 外部（含前端、评测）无法区分"闲聊"和"缺信息澄清"，我第一版评测就误判了 5 条 |
| W3 | `episode.py:131` | `recall()` 只取 `ORDER BY id DESC LIMIT 200` | 超过 200 条后，更早的记忆**永远不会被召回**，且这个上限没有任何提示 |
| W4 | `episode.py:160` | `hit_count` 随召回递增且无衰减 | 形成"越召回越容易被召回"的正反馈（实测 57 次 vs 0 次） |
| W5 | `radar/gate.py:263` | 缺 3 个以上字段判 `unknown` | 逻辑正确，但 80 个岗位里 `unknown` 有 8 个、`no_company` 23 个，说明**采集质量是雷达精度的上限** |
| W6 | `agent.py:328` | `near_miss` 用 `sim >= 0.45` 硬阈值 | 与召回侧"无阈值"不一致，同一套相似度在召回和兜底用了两套标准 |

## 六、已达到产品标准的项

这些经得起检验，不需要再改：

- **匹配规则引擎**：63 条用例 96.8%，否决 precision/recall 双 100%，21 个否决全部正确
- **槽位抽取的精准度**：precision 100%，13 条负例零误报，"这次先看看深圳的"这种临时条件也能正确不记

- **意图与城市抽取**：单轮 100%，多轮槽位继承（"那广州呢"）正确
- **雷达口径一致性**（前一轮已验证）：80 个岗位列表判定与单条判定 100% 一致
- **回复不编造、不贴链接**：4/4，模型没有幻觉岗位
- **降级路径**：LLM 失败时 `_compose()` 退回模板，一定给得出回复
