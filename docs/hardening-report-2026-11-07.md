### 2.1 规则边界 19 条（eval/cases_hard.jsonl，run_eval.py 新增 --cases）

专打既有 63 条没覆盖的边界，期望值全部依据 rules.py/engine.py 实现逐条核实后编写：

| 类别 | 覆盖的边界 |
|---|---|
| 城市边界 ×6 | 区划后缀（佛山市顺德区）、短串包含（北京 ⊂ 北京海淀）、**省份前缀不算同城**（广东省深圳市 ≠ 广州）、异地开关、兜底路径（简历城市 vs 岗位区划）、「全国」按远程 |
| 学历边界 ×5 | 超出不否决（博士投本科岗）、**等于不否决**（大专投大专岗）、统招三态（false 不校验 / true+未注明 → 待确认）、学历未知 × 学历不限 |

| 性质边界 ×2 | 「校招」不在拦截清单（文档化语义）、空性质 |
| 一票多否决 ×1 | 学历+城市+性质三条否决**并存不遮蔽**（expect_rules_count=3） |

## 三、缺陷与修复

### 3.1 【产品·中】off-topic 不拉回（第一轮抓到）

**现象**：hard-offtopic-04 问"帮我写个快速排序"，返回 **923 字完整代码块**。
**归因**：诊断文档 4.6 早已规划（「与求职无关的问题，一句话回应后拉回主题」），但只写进了文档、从未改代码 —— 既有 63 条规则用例和 8 条基线场景全都没测 off-topic，所以一直没被发现。
**修复**（`backend/app/chat/agent.py` PLAN_SYSTEM_PROMPT）：chat 出口明确定义"不执行任务本身、不写代码、60 字以内"。
**复测**：回复变成「写代码不归我管哈～不过刷题多半是为了面试吧？要不要我帮你看看岗位？」→ 10/10。

### 3.2 【产品·中】召回背景被当成本轮意图（第二轮抓到，修复过程暴露）

**现象**：第二轮基线 `route-clarify-06` 回归 —— 空画像问"帮我看看有什么岗位"，模型把情节召回里的历史方向（深圳 AI Agent 后端）当成本轮意图直接检索出 4 个岗位；提示词明文规则是"intent 和历史槽位都没有方向才 clarify"，**召回背景既不是 intent 也不是槽位**，模型越权了。
**归因**：规则一直如此，但只有当上下文里恰好有相似的历史情节（召回命中）时才触发。第一轮跑基线时未触发、第二轮触发了 —— 温度 0 下 prompt 前缀变化引发的边界漂移。
**修复**（同文件）：提示词补一条「intent 只能来自用户本轮消息或已有会话槽位；【过往结论】只是历史参考，用户没说方向时宁可先问一句（问句可带旧方向作选项）」。
**复测**：基线 8/8 **连跑两遍**均绿（稳定性确认），加难 10/10 不受影响。

### 3.3 【测试过期·低】基线两条分数下限没跟上特性（第一轮发现）

`mix-03` 期望 ≥80 实测 74、`mix-05` 期望 ≥95 实测 82 —— README 记载的"技能分母过小按绝对数封顶"特性上线后，这两条用例的分数下限没有跟着更新，**评测集在 HEAD 上本来就是红的**。校正为 70/80 并在 note 里写明校正原因与日期（保留回归价值：分数再往下掉仍会被抓住）。

### 3.4 【测试笔误·低】hskill-05 期望写错（第一轮发现）

空技能清单：rules 层 `check_must_skills` 返回 PASS，但引擎层对"无任何技能信号"整体降级 NEED_CONFIRM（engine.py `no_skill_signal`，有明确理由文案）。期望按引擎层决策改为 confirm，note 记录两层语义差异。

### 3.5 【量具·低】judge rubric 缺 off-topic 语义（第三轮发现）

加难套件 judge 首评 0.933：唯一被标的正是 hard-offtopic-04 的拉回话术（"检索为空却推销岗位"）——评审词表没有 off-topic 语义，把**产品设定的正确行为**判成了推销。修正 judge rubric（拉回求职主题不算推销/不贴题）后复评 1.000。这是"评测量具也要跟着被测系统的设计走"的一个实例。

## 四、并发结论（如实记录）

- T3 去重：**确认已修复**（唯一键 + 幂等返回），is_new 语义正确。
- T1/T2 的读-改-写窗口（SELECT → Python 合并 → UPSERT）：在 6-8 并发下**未显现丢失更新** —— 写路径内无 LLM 调用、窗口极短是主要原因。按本项目"有实测数据才改代码"的纪律，**不加锁**，但作为已知限制记录：理论上仍存在交错窗口，若未来写入路径变长（如在事务内等待外部调用），应加 `SELECT ... FOR UPDATE` 并按 key 排序获取锁（避免多槽位交叉死锁）。

## 五、复现方式

```bash
# 三套加难
python eval/run_eval.py --cases eval/cases_hard.jsonl        # 19 条规则边界
python eval/run_scenarios.py --scenarios eval/scenarios_hard.jsonl   # 10 条对抗场景
python eval/run_concurrency.py                               # 并发竞态（起真实 uvicorn）

# 全量回归（基线）
python eval/run_eval.py                                      # 42 条主评测
python eval/run_scenarios.py                                 # 8 条基线场景
python scripts/check_episode_recall.py                       # 12 条离线（不需库）

# 质量评判
python eval/judge.py eval/results/scenarios_<最新>.json --compare eval/results/judged_<旧>.json
```

各轮原始日志：`eval/results/round1_*.log` / `round2_*` / `round3_*`；场景与 judge 报告均为时间戳 JSON。

## 六、遗留与建议

1. **judge 与被评系统同源**：本报告的 judge 数字用于回归对比，不作为绝对质量声明（换强模型只改配置）。
2. **对抗场景可继续加压**：本轮没做"注入式记忆投毒"（用户消息伪装系统指令）与"超长对话槽位漂移"，前者语义边界需要先定产品口径。
3. **route-clarify-06 值得多跑几遍**：它是当前唯一依赖模型边界行为的断言，进 CI 后建议每次跑 2 遍取一致结果。
