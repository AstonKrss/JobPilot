## 二、情节召回正反馈修复

### 问题（诊断文档 R5，修复方案 4.5）

初版权重 `0.55 相似 + 0.25 时间 + 0.20 频次` 有两个结构性偏差：

1. **正反馈**：`hit_count` 只增不减、5 次即饱和，饱和后频次项是永久加分。实测两条既有记忆 58/17 次命中，频次项永远满分 —— 一条 cos=0.764 的记忆排在 cos=0.494 之后（后者靠命中次数霸榜）。
2. **无下限**：天气、写代码这类无关 query 也稳定返回 3 条（最高 sim 仅 0.29），噪音照进 prompt。

### 修法

| 改动 | 内容 | 为什么 |
|---|---|---|
| 权重重配 | 0.55/0.25/0.20 → **0.70/0.20/0.10** | 相似度是主信号，频次只表达"常用"，不该与相似度同量级 |
| 频次衰减 | `min(命中/5,1) × exp(-距上次召回天数/60)` | 霸榜优势从永久 0.20 变为冷置 90 天后仅 0.022；半衰期比时间项长（60 vs 30 天），因为它表达"长期有用"，衰减只为压正反馈 |
| 相似度阈值 | `sim < 0.35` 直接不召回；全低于阈值返回空 | 在**过滤**而不是压分 —— 压 0.1 分还是会被时间项捞回来（教训）；宁可不带背景，不塞噪音 |
| 可测试性 | 打分抽成纯函数 `_score_one`，时钟可注入 | 离线回归不依赖库、向量模型与网络，结果不随日期漂移 |

### 实测（同一基准：e4 三组对照，12 条测试记忆 + 2 条真实记忆，跑完精确还原）

| 指标 | 旧公式 | 新公式 |
|---|---:|---:|
| C 组（纯语义）recall@1 / @3 | — / 75% | **91.7% / 100%**（MRR 0.944，P@3 1.0） |
| A 组（霸榜记忆在场）recall@1 / @3 | 0% / 41.7%¹ | **41.7% / 58.3%** |
| 无关 query 注入记忆（live 验证） | 3 条 | **0 条** |
| 翻车案例（0.764 vs 0.494） | 复现（0.6833 > 0.6760） | **翻正**（0.6071 < 0.6401） |

> ¹ A 组旧值为诊断文档验收标准表记录的现状基线。A 组新值未达 C 组水平的原因：id 匹配口径下，真实记忆与种子记忆对同一 query 都相关、互相挤位（如「正浩那个实习还值得投吗」），属于标注口径的已知限制（诊断文档阶段 2 教训 2 同源），不是排序错误。

### 回归锁定

`scripts/check_episode_recall.py`（12/12）：阈值三个负例 + 边界值、翻车案例**双向断言**（旧公式必须复现翻车、新公式必须翻正，任一不成立都说明对问题的理解有错）、频次衰减上界（0.0223 < 0.03）、最近使用保留加成（不搞一刀切清零）、`last_hit_at` 缺失回退 / 未来时间 / None 处理。

## 三、会话级端到端评测

### 与既有评测的分工

| | run_eval.py（既有） | run_scenarios.py（新增） | judge.py（新增） |
|---|---|---|---|
| 层级 | 规则级 | 链路级 | 回复质量 |
| 输入 | 构造的简历×岗位对 | 多轮真实对话 | 场景产出的回复 |
| 断言 | 判定口径 | **库里变了没有 / 路由走对没有 / 回复守约没有** | 有没有编造、语气对不对 |
| 依赖 | 无（纯函数） | 数据库 + LLM key | 数据库无、LLM key |

诊断文档 R3 的教训是这条链路的立项理由：记忆写入曾经是接口而不是行为，「接口有测试就算过」挡不住「链路压根没接」—— 副作用的验收标准只能是库里多了什么。

### 场景集（eval/scenarios.jsonl，8 条）

| 场景 | 断言的核心行为 |
|---|---|
| mem-exclusive-01 | 排他表述覆盖画像、旧值进历史、回复说明写入了什么 |
| mem-search-02 | 祈使句搜索不改写长期偏好，但本轮条件真的生效（steps 里出现） |
| mem-additive-03 | 补充表述合并进数组，旧值保留 |
| mem-tentative-04 | 不确定表述挂起不写库，回复里问回来（挂起不能是死胡同） |
| mem-persist-05 | 多轮：第一轮写的偏好，第二轮检索真的按它执行 |
| route-clarify-06 | 无方向信息先反问，不用空意图把全库倒出来 |
| route-chitchat-07 | 闲聊走 chat 出口：不检索、不动画像 |
| reply-no-url-08 | 真实检索链路下回复正文不贴 URL（结构约束遵守） |

### 隔离纪律（每条场景独立）

快照 `user_profile` 全表 + `user_profile_history`/`conversation` 的 max(id) + `episode` 命中计数 → 清空画像写入场景基线 → 逐轮 POST `/api/chat` → 断言 → **精确还原**。评测最忌讳留下被自己改过的数据：下一次评测会以污染后的状态为基线，越跑越离谱（check_memory_wired.py 既有纪律的推广）。

### 结果

首跑 **8/8 通过**（41.0s，LLM 成本约 ¥0.04）。回复内容印证链路行为：「已写入画像：目标城市 → 佛山」「想找什么方向的岗位？」「这个方向暂时没有你能投的岗位」。

## 四、LLM-as-judge

### 四个维度（硬断言管"对不对"，judge 管"好不好"）

| 维度 | 判什么 | 为什么不做成硬断言 |
|---|---|---|
| fabrication 编造 | 回复中的岗位/公司/分数/城市能否在检索结果里找到 | 自然语言变体太多，正则会误伤 |
| tone 语气 | 没结果时直说，不把投不进的岗位当推荐 | 同上 |
| relevance 贴题 | 是否回应了这轮的问题 | 同上 |
| clarity 缺口 | 有 blocked 岗位时是否说清卡在哪（不适用则标 na，不计入分母） | 同上 |

### 方法学限制（写在模块 docstring 首位）

judge 与被评系统当前共用同一模型（网关只有这一个），同源自评有系统性偏差 —— **数字用于回归对比（改 prompt 前后各跑一遍），不作为绝对质量声明**。换强模型只需改配置，rubric 与管线不变。

### 结果与对比

首跑 9 轮：编造 0.889 / 语气 1.000 / 贴题 1.000 / 缺口 1.000（n=3）。修复 §五 的缺陷后重跑并 `--compare`：

```
编造: 0.889 → 1.000 ↑ +0.111
语气: 1.000 → 1.000 → +0.000
贴题: 1.000 → 1.000 → +0.000
缺口: 1.000 → 1.000 → +0.000
整体: 0.889 → 1.000 ↑ +0.111
```

## 五、新发现并修复的缺陷

### 5.1 【低】回复编造数据属性：「城市信息缺失」

**现象**（judge 首跑，mem-search-02）：回复称「资深后端工程师（80 分），但它的城市信息缺失，需要点开核实是否在深圳」——而检索结果里该岗城市就是深圳。

**根因**：不在模型，在数据装配。`REPLY_SYSTEM_PROMPT` 要求按「岗位名（城市，分数）」格式输出，但 `_compose` 拼给模型的结果行只有「岗位名（公司，分数）」，**城市字段从未传入**。模型被要求输出一个它没拿到的字段，只能猜 —— 猜对了是运气，猜错了就是编造。

**修法**（`backend/app/chat/agent.py`）：`_compose` 新增 `cities_by_id` 参数随结果行传入；城市缺失时明写「城市未标注」，不让模型对缺失做推断。修复后重跑：该轮判定翻绿，编造率 0.889 → 1.000。

**为什么值得记**：这是「提示词要求的输出格式」与「实际提供的数据字段」不一致的错位 —— 单测抓不到（不跑模型）、人眼难发现（这条恰好猜"对"了直觉）、judge 一次就抓到。评测体系的价值在这一条上完成了自我证明。
