> 这份是技术版，术语较多。想快速知道「修好没有」看 [一页看懂-评测问题与修复.md](一页看懂-评测问题与修复.md)。

- **复核对象**：`docs/agent-eval-report-2026-10-29.md`
- **复核时间**：2026-10-29 20:45 – 21:10
- **复核方式**：逐条对代码（不看结论只看实现）+ 三个离线实验（本地向量 / 纯函数，不调模型、不写库）
- **结论**：报告**测到的现象全部成立**，五项 P0/P1 我都复现了。但「为什么」那一层它只挖到一半 —— 报告把 P0-2 和 P0-3 当成两个问题，它们其实是**同一个结构缺陷的两个出口**；它给的第一优先级修法（提高 sim 权重）在现有结构下**不会生效**。

## 一、我补的三个实验与结论

### 实验 1：意图相似度到底有没有区分度

报告的 P0-3 里写「sim 的差异只有 0.023」，据此认为意图在数值上无法影响排序。我用本地 bge 对全部 80 个岗位重算了一遍：

| 意图        | sim min | sim max |        极差 |
| --------- | ------: | ------: | --------: |
| 产品经理      |   0.259 |   0.655 | **0.396** |
| Python 后端 |   0.262 |   0.752 | **0.490** |
| 佛山 后端 实习  |   0.275 |   0.897 | **0.622** |
| 数据分析      |   0.198 |   0.698 | **0.500** |

**极差不是 0.023，是 0.4–0.6。** 报告观察到的 0.023，是它只在**返回的那 3 条**上算差 —— 而那 3 条是被排序截断后的结果，属于幸存者偏差。

这个修正很重要，因为它推翻了一个直觉：向量并不是「没有区分度」，它区分得很好。问题在于**它区分出来的岗位，根本没进候选集**。

### 实验 2：80 个岗位走到「可排序」这一步还剩几个

用线上同一套 `rank()`、同一份简历（#6）、同一份硬编码 prefs 跑：

```
决定分布：pass 1 / confirm 11 / reject 68
否决原因：job_nature 38 次、must_skills 33 次、education 5 次（有重叠）
passed 集合 = 12 个
```

**对话检索实际是在 12 个岗位里挑 6 个，不是在全库 80 个里排。**

报告的 P0-3 说「检索实际是按简历匹配度排序」，更准确的说法是：**它连全库排序都不是，是"12 个里排序"**。这也解释了那个异常现象 —— `资深后端工程师` 在 8 个意图里出现 7 次：12 个候选里简历匹配度最高的那个，换哪个意图都在前 6。

### 实验 3：那 4 个产品岗，是被谁挡掉的

| job | 标题             | 决定     | 卡在             |
| --: | -------------- | ------ | -------------- |
|  22 | 安防产品-网络销售      | reject | must_skills    |
|  52 | 产品实习生          | reject | **job_nature** |
|  84 | 产品顾问（财经数字化）    | reject | must_skills    |
|  86 | B端产品经理（价格模块方向） | reject | must_skills    |

**4 个全不在 passed 里。** 所以「我想找产品经理」返回 0 个产品岗，跟 sim 权重、跟排序公式**一点关系都没有** —— 它们在排序发生之前就已经出局了。

把 prefs 换成「实习可投、不外包」再跑一遍，`52 产品实习生` 从 reject 变成 confirm，但 84/86 仍然被 `must_skills` 挡着。

## 二、根因：一个结构缺陷，四个出口

报告列了 5 个 P0/P1。我认为它们收敛到 **4 条结构性原因**，其中前两条是同一个东西。

### R1（核心）：`REJECT` 一职两用 —— 判定结论被拿去当召回过滤器

`rank()` 返回的 `reject` 原本回答的是「**这份简历投这个岗位有没有胜算**」。这是匹配页的问题，答案是二元的，很合理。

但对话检索把这个 `reject` 直接用来**过滤候选集**：

```python
passed = [r for r in results if r.decision is not Decision.REJECT]
...
top = passed[:6]
```

于是两件毫不相干的事情被压进了同一个枚举：

| 岗位            | 作为「能不能投」的判定      | 作为「用户要找的方向」的召回         |
| ------------- | ---------------- | ---------------------- |
| 52 产品实习生      | reject（你设的是只找全职） | **应该出现**，用户明确说要看产品岗    |
| 84 产品顾问       | reject（必备技能 0/5） | **应该出现**，并告诉他「要投得先补什么」 |
| 55 Java 开发实习生 | reject（同上，性质不符）  | **应该出现**，这是用户最想要的      |

这说明 **P0-2 和 P0-3 是同一个 bug**：报告看到的是「实习岗没出现」和「产品岗没出现」，两个症状，一条根因 —— 判定层越权做了召回层的决定。

对比一下数量级差异：报告说「库里躺着 5 个佛山的开发实习岗被否决」。实测 `job_nature` 一条就否决了 **38 个**岗位（全部实习岗 + 少量兼职），而 passed 只剩 12 个。整个实习池在召回阶段就被清空了。

### R2：意图以「末位小数」的形式进入排序，且截断发生在它生效之前

现有排序：

```python
passed.sort(key=lambda r: (group_order[r.decision], -((r.score or 0) + sim * 10)))
```

三个数值事实：

| 项                | 实际量级                                    |
| ---------------- | --------------------------------------- |
| `score`（简历匹配分）跨度 | 40 – 80，**40 分**                        |
| `sim × 10` 的满分影响 | 0–10 分，passed 内部实测极差 0.27 → **约 2.7 分** |
| 截断               | `top = passed[:6]`，发生在排序**之后**          |

所以即使把权重从 10 提到 100：`sim` 差异 0.4 → 40 分，与 score 跨度同量级，**会开始生效，但同时把「标题相似」变成主导信号** —— 一个叫「产品顾问」的岗位会压过真正匹配你技能的「Java 开发」。这不是调参能解决的区间，它是两种信号在打架。

真正的顺序错了：**意图应该决定"看哪一堆"，匹配分决定"先投哪一个"**。现在反了 —— 先按匹配分把池子削到 12 个，再让意图在残渣里微调。

### R3：记忆写入从未接入对话循环 —— 它是接口，不是行为

报告这条完全正确，我复核确认：

```
observe()                 → 只在 api/profile.py:39 的路由里被调用
summarize_conversation()  → 只在 api/memory.py:25 的路由里被调用
chat/agent.py             → 全文没有这两者的调用
```

这不是"忘了加一行"，是**实现形态选错了**：记忆写入被做成了 REST 接口（可以由用户/外部主动触发），而产品需要的是对话的**副作用**。接口是"可以被调用"，副作用是"一定会发生"。两者的验收标准完全不同 —— 接口有测试就通过，副作用要看"用户说完话之后库里多了什么"，而这一条从来没被断言过。

于是出现报告里最讽刺的一幕：助手回答「记住了：以后只找佛山，排除外包」，数据库里 cities 仍是 `["广州","深圳"]`。

### R4：L0 门禁用 AND 组合两个不完整的词表 —— 结构性不可写

```python
if not any(w in text for w in SIGNAL_WORDS):        return False   # 信号词
return any(hint in text for hints in SLOT_HINTS.values() for hint in hints)  # 槽位词
```

`ALLOWED_KEYS` 有 10 个槽位，`SLOT_HINTS` 只覆盖 5 个。**另外 4 个（`target_roles` / `hard_constraints` / `excluded_companies` / `accept_relocation`）没有任何 hint 词** → 任何提到它们的句子，第二道判断必然返回 False → 永远进不了 L1。

报告说「5 个 FN 全部是 L0 挡的，不是模型抽错」，这是对的；但它没说的是：**这 4 个槽位的 recall 在结构上就是 0**，不是"漏检多"，是"不可写"。库里只有 3 个槽位有值，不是用户说得少。

根子在于：L0 的本意是**省钱**（避免每句都调模型），但它同时套上了**正确性**的责任。当词表不全时，省钱的门禁就变成了"只有系统已知的说法才能被记住"。

### R5：情节召回的三重偏差（报告的四条根因，我合并成三条）

```python
score = 0.55 * sim + 0.25 * time + 0.20 * min(hit_count / 5, 1.0)
```



| 偏差        | 机制                            | 报告给的证据                                  | 我的补充                                        |
| --------- | ----------------------------- | --------------------------------------- | ------------------------------------------- |
| **正反馈**   | `hit_count` 每次召回 +1，无衰减、5 次饱和 | id1=57、id2=17                           | 饱和后仍是满分 0.20，等于永久加分。**库越大偏差越大**，这是自我强化      |
| **无阈值**   | `return top` 无条件给 3 条         | 天气 query 也返回 3 条，最高 sim 0.29            | 我在实验 1 里测到 `min sim` 常低到 0.198，说明无关记忆确实能被注入 |
| **长摘要趋中** | 摘要越长覆盖词汇越广，向量越靠语料中心           | 正浩 EcoFirst 对 7 个不相关 query 都在 0.39–0.57 | 这是摘要式记忆的固有陷阱，不是权重问题                         |

三组对照实验（A/B/C）证明的是：**排序本身可用（C 组 recall@3=75%、P@3=1.0），坏在"霸榜"和"无下限"**。所以修法不是调 0.55 这个数，而是「先加阈值截断，再让频次衰减」。

### R6：约束写在 prompt 里，但没有任何一层兜底

- 「控制在 250 字以内」→ 实测 1/4 遵守（306/504/388 字）
- 问「帮我写个快排」→ 写了 504 字带代码块，没有拉回主题

共同点：**这两条都只有提示词这一个执行者**。而模型对"字数"这类连续量约束的遵守率天然不高（它不数数），对"结构"类约束（几个区块、每块几行）反而遵守得好。

### R7：有状态，但没有状态机

`recall_block` 只在会话开场召回一次并写死进 `slots`（W1）。这是**为了 KV Cache 前缀稳定做的刻意取舍**（README 里有记录），不是疏忽。但代价是：长会话里用户改主意后，旧记忆一直挂在 prompt 上，新记忆进不来。报告列为 P1，我认为该列为**已知限制**而不是缺陷 —— 除非会话变长，否则不值得为它破坏缓存。

## 三、我对报告的两处修正

| 报告说法                              | 我的复核                                                                                                                                   |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 「sim 的差异只有 0.023，乘以 10 等于 0.23 分」 | **不成立**。那是只在前 3 条上算的。全库极差 0.4–0.6，passed 内部 0.27–0.42。结论（意图无法影响排序）仍然成立，但**理由不同**：不是因为向量没区分度，是因为目标岗位不在候选集里，且 score 跨度（40）远大于 sim 项（2.7） |

## 四、修复方案

### 4.1 召回与判定分离（解决 R1 + R2，即 P0-2 与 P0-3）

```
用户意图
   │
   ├─① 召回层（不看简历，只看方向）
   │   向量 top-25 ∪ 关键词命中（标题优先）∪ 城市过滤
   │   → 候选集 15–30 个
   │
   ├─② 判定层（跑现有 rank()，口径不变）
   │   pass / confirm / reject —— 每个岗位都带"客观结论"
   │
   └─③ 输出层（三栏，而不是一栏）
        A. 方向对 + 能投        → 正常列出，按匹配分排
        B. 方向对 + 投不进      → 列出并写明卡在哪（这是新东西）
        C. 方向不对 + 能投      → 不列（用户没问这个方向）
```

关键变化只有两处，但性质变了：

1. **`reject` 不再是过滤器，而是标签。** 方向对的岗位即使投不进也要展示，并说清原因。这直接消灭 P0-2：实习岗会以「方向对，但你当前设置只找全职」出现，用户看到就会去改设置。
2. **排序改为两段**：先由方向决定候选，再在候选内按 `决策组 → 匹配分` 排。意图不再和匹配分抢同一个加权和，`sim` 因此不需要调权重。

为什么这是对的而不是"又加一层"：三栏里的 B 栏其实是产品价值最高的部分 —— **「你想去但还差什么」比「你能去哪」更有用**。匹配页已经在算这件事（缺口清单），只是一直没有出口。

### 4.2 prefs 从画像装配（P0-2 的另一半）

现在的 prefs 是 5 个手写常量。改成 `_prefs_from_profile(prof, cities, stage)`：

| 开关                   | 取值来源                              | 缺省                                  |
| -------------------- | --------------------------------- | ----------------------------------- |
| `accept_outsourcing` | 画像 `accept_outsourcing`           | 缺省 True（宁可多给）                       |
| `accept_internship`  | 画像 `job_nature` ∈ {实习, 不限} → True | 缺省 True（**这是原 bug 的反面**：原来缺省 False） |
| `target_cities`      | 本轮 `cities`，为空则用画像                | 空 = 不过滤                             |
| `accept_relocation`  | 画像 `accept_relocation`            | False                               |

这条单独做也有独立价值：**它让「用户说了实习」立刻生效，不依赖记忆写入链路是否打通**。

### 4.3 记忆写入（P0-1）—— 有一个免费的位子

报告建议「在 handle_message 里接入 observe()」，但那意味着每轮多一次模型调用。以服务商 6 tok/s 的实测速度，等于每轮 +2~3 秒，P90 会从 8.3s 涨到 10s+。

**更好的位子：让 PlanAgent 顺带输出。**

它已经在读用户原话、已经在输出 `intent` / `cities` / `clarify`，做的是同一类工作（理解这句话）。加一个字段 `profile_updates: [{slot, op, value, modality, evidence}]`，**零额外调用、零额外延迟**。

代价是 prompt 变长（约 +300 token）且职责变混（规划 + 抽取）。收益是延迟不涨。我倾向这个方案，因为记忆写入的最大风险不是抽错（precision 100%），而是**它压根没运行** —— 先让它跑起来，再谈延迟优化。

会话级摘要（episode）仍然需要边界。浏览器里没有可靠的"会话结束"信号，可行的做法是：**下一条消息与上一条间隔 > 30 分钟时，先把上一段摘要掉**。这不是完美的边界，但它能在"用户下次回来问别的事"时把上次的结论落成记忆。

### 4.4 L0 门禁（P1 第一条）

三件事，按收益排序：

1. **补齐 4 个槽位的 hint 词表**（`target_roles` / `hard_constraints` / `excluded_companies` / `accept_relocation`），这是纯亏的地方，不补就没有 recall。
2. **把 AND 改成「信号词 OR 强槽位词」**：强槽位词 = 明确的枚举值（城市名、"实习"、"外包"、"大厂"），弱槽位词（"学历"、"工资"）保持 AND。
3. 补 `SIGNAL_WORDS`：「我是」（M05 漏检）、「暂不 / 不考虑」（M07）、「优先」（M10）。

预期 recall 61.5% → 85%+，precision 会掉一点（估计 95% 左右）。这个交换划算：漏记的代价是"下次还得重说"，误记的代价是"系统按错的标准筛岗位" —— 前者用户体验差，后者更糟，但 precision 100% 本身说明现在的门禁过严了。

### 4.5 情节召回（P1）

三步，从便宜到贵：

| 改动         | 一句话                                                                |
| ---------- | ------------------------------------------------------------------ |
| 加阈值        | `sim < 0.35` 直接丢弃；全部低于阈值就返回空，让 prompt 干净                           |
| 频次衰减       | `freq = min(hit/5,1) * exp(-days_since_last_hit/60)`，或干脆去掉 freq 项  |
| 权重重配       | `0.70 sim + 0.20 time + 0.10 freq`，改完用 e4_weight_ab 的三组对照复测        |
| 摘要限长 + 双向量 | summary ≤ 120 字；向量取 `max(cos(topic), cos(topic｜summary))`，压住"万能磁铁" |

先做前两步（一小时），拿 C 组数据复测；如果 recall@1 到 50% 就停手，不再动权重 —— 记忆不是搜索，不需要极致召回。

### 4.6 回复约束（P2）

- 把「250 字以内」改成**结构约束**：「1 句结论 + 最多 5 行岗位 + 1 句建议」。模型不擅长数数，擅长数行。
- off-topic：PlanAgent 的 chat 出口加一句「与求职无关的问题，一句话回应后拉回主题」。
- 兜底：`_compose` 之后做一次长度检查，超 400 字按分句截断并标注「已省略」。**不静默截**，否则用户不知道为什么少了一半。

### 4.7 需要加的两个测试（现在完全没有）

这一轮暴露的最根本问题不是任何单个 bug，而&#x662F;**"记忆写入"这条链路从来没有断言过**：

```
新增 e9_memory_wired.py：
  POST /api/chat {"text": "我不接受外包，以后只找佛山的岗位"}
  → 断言 user_profile 里 cities 含「佛山」、accept_outsourcing 为 false
  → 断言 user_profile_history 新增 ≥1 条

新增 e10_recall_wired.py：
  构造一个 intent 明确的查询
  → 断言返回结果里至少 N 个岗位的标题向量 sim 排在全库前 20%
  → 这条直接把 P0-3 变成回归项，而不是靠人肉评测发现问题
```

这两条比任何单点修复都重要：**能被断言的东西才会一直对**。

| --------- | ------------------------------------- | --------------------- | ------------------------------------- |
