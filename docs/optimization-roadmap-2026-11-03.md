## 为什么不加 MQ / 分布式

这是本文最重要的一个"不做"，先说清楚理由。

1. **README 自己已经论证了不需要。** 技术栈一节写的是"单机单用户，异步够用，无需队列"——这个论证成立。面试官读完 README（它足够好，一定会被读）会追问"为什么要 MQ"，答不出业务理由的那一刻，前面所有"每个决策有实测数据"积累的可信度全部归零。
2. **简历驱动开发是减分项，而且可被识别。** 有经验的面试官对"项目里堆了 Kafka/Redis/K8s 但说不出为什么"极度敏感。反过来，"知道什么时候**不用**重架构"是更高阶的信号。
3. **分布式的唯一正当入口是多用户化。** 届时队列、租户隔离、限流都是真需求。但那是另一条产品线，成本极高且会稀释 agent 主线，只在投递"Agent 平台工程"类岗位时才值得考虑（见 P3）。

> 想聊 MQ 的面试话术（P1.3 做完后自然成立）："长任务我用 Postgres 队列表解决，因为单机单用户下 Kafka 的分区与吞吐没有对象；如果要多用户，我会先加鉴权和租户，队列再换轻量 MQ——先有规模再有架构。"

## P1 · Agent 深度三件事（1–2 周，核心投入）

### P1.1 评测体系升级 —— 和"调 prompt 的"划清界限

**为什么是第一优先级**：2026 年 Agent 工程师岗位面试里，"你怎么知道你的 agent 变好了还是变坏了"是必问题。你有 63 条规则级用例和一个诚实的免责声明，往上做两层就能完成质变。

**做什么：**

1. **会话级端到端黄金集**（新建 `eval/scenarios.jsonl`）
   - 多轮对话用例：`[{"turns": ["以后只找广州", "帮我看看后端的"], "assert": {"profile.cities": ["广州"]}}]`
   - 断言类型：画像槽位写入 / fit·blocked 双栏内容 / direction_hits 语义 / 回复不含编造的 job_id
   - 这就是把 `scripts/check_memory_wired.py` 的思路（真的发一句话再查库）产品化成可批量跑的用例
2. **LLM-as-judge 回复质量评测**（新建 `eval/judge.py`）
   - 用强模型按 4 个维度给回复打分：是否编造（引用不存在的岗位）/ 方向命中率 / 错误推荐语气（方向全不匹配时是否还在"推荐"）/ 是否说清了差什么
   - judge 结果入库（新表 `eval_run`），**每次改动前后各跑一遍，存对比**——形成质量曲线
3. **修复情节召回正反馈**（`backend/app/memory/episode.py` 的打分权重）
   - 按 `docs/agent-eval-diagnosis-2026-10-29.md` 里已写好的方案实施：hit_count 饱和 + 衰减 + 相似度下限
   - 修完后在评测集里加 before/after 用例（那条 cos=0.764 输给 0.494 的案例直接变成回归用例）

**简历产出**："建立会话级评测 + LLM-as-judge 质量体系，定位并修复召回正反馈缺陷，方向命中率 X% → Y%"——这是有过程、有数据、有修复的完整故事。

### P1.2 工具层 + 对照实验 —— 从"不错的项目"到"有实验的项目"

1. **MCP server**（新建 `mcp_server/`）
   - 把已有能力封装成 MCP 工具：`search_jobs(intent, cities)` / `match_job(job_id, resume_id)` / `radar_screen()` / `get_gap(job_id)`
   - 工具 schema、错误语义（404/409 你已经有）、进度通知对齐 MCP 规范
   - 效果：Claude 等 client 能直接驱动这套系统。MCP 是当前 JD 高频词，且这里理由正当——给 agent 的标准工具接口
2. **ReAct vs 规划管线对照实验**（新建 `eval/ab_agent_arch.py`）
   - 同一批任务（从黄金集取），跑两个实现：现有"PlanAgent + 确定性管线" vs function calling 实现的 ReAct 自主循环
   - 记录四个指标：任务成功率 / 端到端延迟 / token 成本 / 失败模式分类（漏检哪一步、是否陷入多余轮次）
   - 结果写成 `docs/benchmark-agent-arch.md`

**这是整个规划里最能打动面试官的一条**。README 里"为什么不做自主循环"现在是三条论断（步骤固定 / 6 tok/s / 出口必须硬），实验之后变成受控数据。面试叙事从"我选择了 A"升级为"我做了 A/B 对照，B 在 X 场景漏检率是 A 的 N 倍、成本 M 倍，但在 Y 场景 A 反而吃亏"——最后这半句尤其值钱，说明实验没有预设立场。

### P1.3 异步任务层 —— "队列"的正当版本

**真实需求（不是为加而加）**：OCR 1–2 分钟、批量匹配 18.4s、HR 监控 10 分钟轮询，现在全是进程内阻塞或轮询。

- Postgres 队列表 `task_queue(id, type, payload, status, progress, result, created_at, claimed_at)` + 独立 worker 进程
- 任务类型：简历解析（含 OCR）/ 批量匹配 / 定时雷达 / 批量改写
- 支持取消、断点恢复（`stage_snapshot` 你已经有，直接衔接）、进度经 SSE 推送
- **刻意不引入 Kafka/RabbitMQ**，并把"为什么 Postgres 队列够了"写进 design-decisions——面试聊到 MQ 时这就是你的答案

## P3 · 可选分支（仅当目标岗位偏后端基建）

多用户 SaaS 化是"分布式"的唯一正当入口：鉴权（JWT）→ 租户隔离（schema 或行级）→ worker 池横向扩容 → 限流。工作量 2 周起步，且会稀释 agent 主线。

**决策规则**：目标岗位 JD 里出现"Agent 平台 / LLM 基础设施 / 多租户"才做；纯"大模型应用开发 / Agent 开发"岗不做，把时间花在 P1。

### P1.1 评测体系 —— 已完成

**1. 情节召回正反馈修复**（诊断文档 4.5 的方案落地）

- 真实库复测（e4 三组对照，同一基准）：纯语义组 recall@3 **75% → 100%**（recall@1 91.7%、MRR 0.944、P@3 1.0）；无关 query 注入 **3 条 → 0 条**（live 验证）

- 首跑 **8/8 通过**（41s，约 ¥0.04）

**3. LLM-as-judge**

- `eval/judge.py`：对场景回复按四维评判（编造 / 语气 / 贴题 / 说清缺口），维度通过率落 `eval/results/`，`--compare` 与上次对比。方法学限制（同源自评）已写在模块 docstring
- **第一次真跑就抓到一个真 bug**：回复对有城市的岗位说"城市信息缺失"。根因：REPLY 提示词要求「岗位名（城市，分数）」格式，但 `_compose` 拼的结果行根本没给城市字段，模型只能编。修复（`backend/app/chat/agent.py`：城市随结果行传入，缺失明写"城市未标注"）后重跑，编造率 **0.889 → 1.000**，judge 全维 9/9
